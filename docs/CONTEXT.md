## Открытые проблемы

| # | Priority | Описание |
|---|----------|----------|
| 1 | **High** | **Шесть наборов из семи не рисуются.** `desert`, `mountains`, `mars`, `venus`, `glacier`, `fungal` ждут пропсов от `NexusModeler`; до их прихода предпросмотр показывает отказ, а кожу выгрузить нельзя. Сценарий рабочий, но инструмент урезан до одного набора |
| 2 | Medium | **Шесть скриншотов в галерее `docs/` устарели**: `biome-desert`, `biome-mountains`, `biome-mars`, `biome-venus`, `biome-glacier`, `biome-fungal` сняты с процедурными объектами, которых в приложении на этих наборах больше нет. Обновлю, когда штаб закроет наборы. Обновлён только `biome-forest` — его вид изменился по существу |
| 3 | Medium | **Плотности по слотам в контракте нет.** Одна занятая клетка получает один пропс, слот выбирается равновероятно среди сорока, первые сорок клеток получают по одному каждому слоту. Это вынужденно: выдумывать плотность здесь нельзя, предпросмотр обязан совпасть с игрой. Если игра будет ставить иначе — предпросмотр придётся подвинуть |
| 4 | Medium | **Пропсы не в репозитории.** `props/` в `.gitignore`, файлы читаются из `../NexusModeler` скриптом `npm run props`. В чистой копии репозитория без соседнего проекта лес не покажется — покажет отказ с текстом «выполни npm run props» |
| 5 | Low | Нет LOD: трава (~12 тыс. в лесу) и деревья рисуются целиком на любом расстоянии. На слабом GPU просядет |
| 6 | Low | Нет автоподбора качества: fps показывается, но деградации не происходит |
| 7 | Low | Вода без глубины: нет прозрачности по глубине и пены у берега, только цвет и блик |
| 8 | Low | Нет сохранения состояния: набор, легенда и карта сбрасываются при перезагрузке. Чинится сохранением в хеш URL |
| 9 | Low | Тесты гоняют три размера карты. Стоит добавить прогон на 512×512 — там сцена собирается заметно дольше |
| 10 | Low | Сборка сцены выросла: сетка сглаженной высоты и ridged-мультифрактал в каждой вершине дают 100–310 мс на карте 96×96 (было 41–104). На 512×512 будет заметно медленнее |

## Как устроен конвейер

```
JSON карты
  → parseMap()      проверка размеров, сбор списка символов
  → autoLegend()    угадывание трёх типов клеток
  → applyLegend()   Uint8Array типов + размытые маски дорог и занятых участков
  → applyBiome()    свет, небо, туман, вода, PMREM-окружение
  → buildHeight()   сетка сглаженной высоты S.hAvg — «по чему едет дорога»
  → buildGround()   DataTexture (цвет земли) + PlaneGeometry (рельеф), UV и высоты
  → buildScatter()  для каждого правила набора — места, затем InstancedMesh на каждую часть
  → buildMinimap()  карта типов + рамка камеры
  → applyLayers()   видимость по слоям
```

Ключевое: `terrainH(x, z)` — единственный источник высоты. МешTerrain и расстановка объектов
берут высоту из одной и той же функции, поэтому объекты всегда стоят на поверхности.

## Что такое скин и почему в нём плотности

Скин — один JSON на текущий набор оформления: цвета земли, три числа рельефа, свет,
правила расстановки и `tiles` — сорок слотов набора. Его читает игра, которая сама геометрию
не строит, поэтому в нём **нет перечислений**: ни наборов, ни объектов, ни «известных» имён.
Каждое правило несёт для рисования всё само, включая `builder` — но это имя для чтения
человеком, по нему игра ничего не ищет.

Главное поле — `count`: сколько объектов правила ожидается в блоке `4 × 4` клеток,
посчитанное по клеткам нужного типа. Отдавать параметры шума нельзя: игре пришлось бы
держать вторую реализацию `fbm`, и она разошлась бы с этой на первой же правке набора.

**`cellSize` и `scatter.cell` — разные вещи, путать их нельзя.** `cellSize` — перевод клетки
карты в мировые единицы (`CELL`, сейчас 2); без него игре неизвестен масштаб, ландшафт
вышел бы вдвое мельче, а `blockedLift: 2.5` превратился бы в 1.25. `scatter.cell` —
сторона блока, внутри которого посчитан счётчик, и к единицам мира отношения не имеет.
Величина `CELL` не меняется: решение владельца от 2026-10-04, на нём отстроен весь вид.

Связь с расстановкой прямая и хрупкая:

| Что | Откуда берётся |
|-----|----------------|
| Объекты на экране | цикл в `buildScatter` со случайными числами |
| Пропсы на занятых клетках | `buildProps`: один пропс на клетку, слот равновероятно из сорока |
| Счётчики в скине | `ruleDensity()` — математическое ожидание того же цикла |

Расхождение между первыми двумя ловит тест «кожа выгружается детерминированно…»: он
сравнивает сумму счётчиков с реальным числом **процедурных** объектов. На занятых клетках
счётчики больше не сверяются с картинкой — там пропсы, а у них в контракте нет ни `per`,
ни `scale`. Измеренная пара (карта 96×96, лес): счётчики 13 069 против 13 072 процедурных
объектов, плюс 1659 пропсов и 40 плиток в файле.

## Пропсы: кто их делает, кто их читает и почему так

Геометрию делает `NexusModeler` (`export/land/`: манифест + GLB, имена `land.<сет>.<NN>`),
читает `Burrow3D` и игра. Своих моделей у нас нет, и **откат на процедурные объекты на
занятых клетках запрещён по существу**, а не по правилу: он и есть то расхождение между
картой в предпросмотре и картой в игре, ради которого проекты разнесены.

| Решение | Почему |
|---------|--------|
| `props/` в `.gitignore`, копия скриптом | 1,08 МБ чужих бинарников в репозитории дублировали бы источник истины. Путь к источнику — `PROPS_SRC`, по умолчанию `../NexusModeler/export/land` |
| манифест копируется **побайтово** | второй формат манифеста — это вторая правка в двух местах. Проверку полноты перенесли к себе, а разбор оставили чужой |
| одна занятая клетка = один пропс | плотности по слотам в контракте нет, а выдумывать её нельзя: расхождение вернётся на первой же правке набора |
| первые сорок занятых клеток получают по одному **каждому** слоту | иначе предпросмотр показывал бы не весь набор, а случайные 39 из 40 |
| двухклеточный пропс центрируется на границе клеток | иначе свесится в одну клетку и наполовину вылезет наружу; нет соседа — берётся слот на одну клетку, а не наоборот |
| масштаб пропса = `CELL` | модели `NexusModeler` считаны в единицах игры, где клетка равна единице; у нас клетка — `CELL` мировых единиц |
| причина отказа одна на предпросмотр и выгрузку | иначе рано или поздно скажут разное, и придётся гадать, какое объяснение верно |
| слой переключателя выводится из `kind` | в контракте слоя нет, это наш выбор представления: `tree`/`bush` → растения, `rock`/`debris` → камни, `ruin`/`bone` → декор |

## Как устроен рельеф

`terrainH` складывает четыре независимые части, и порядок между ними важнее каждой по отдельности:

| Часть | Что делает | Чем задаётся |
|-------|-----------|--------------|
| `rawH()` | базовый шум по всей карте + мелкая деталь | `amp`, `freq`, `oct`, `detAmp`, `detFreq` |
| `rawH()` | **горы только на занятых клетках** | `ridgeAmp`, `ridgeFreq`, `ridgeOct` |
| дорога | повод к **сглаженной** высоте, а не доля от шума | `roadFlatten`, `roadSink` |
| обрыв | падение наружу от границы карты | `rimStart`, `rimEnd`, `rimDrop` |

Три свойства, на которых это держится, и почему они не очевидны:

1. **Сглаживание — интерполяция к гладкому полю, а не умножение на маску.** Умножение
   `h *= 1 - roadFlatten*road` давало уторок на границе маски, тем больший, чем выше рельеф:
   ступенька между клетками дороги была 1.9 против 0.4 на свободных. Сейчас дорога берёт
   высоту из сетки `S.hAvg` (тот же базовый рельеф, размытый `boxBlur`), и обе функции
   непрерывны, поэтому ступеньки на границе дороги не возникает.
2. **Обрыв не действует внутри карты.** `out` — расстояние наружу от границы карты в долях
   ширины поля. Пока обрыв считался от края полотна, он съедал край карты: у леса медиана
   высоты по краю была -19.7 при воде -11, то есть карта целиком тонула.
3. **Горы не могут уходить вниз.** `fbmRidged` неотрицателен, поэтому massif только поднимается.
   С вычитанием среднего занятые клетки местами проваливались бы ниже базовой отметки.

Проверяется тестом «край карты, дорога и горы ведут себя как задумано» на всех трёх демо-картах
и всех семи наборах: край выше воды, дорога не грубее свободных клеток, свободные клетки
вдали от занятых остаются в базовом рельефе.

## Две системы координат

Клетки и полотно начинаются в разных местах, и путать их нельзя:

| Начало | Откуда отсчитывается | Где используется |
|--------|----------------------|------------------|
| `originX` / `originZ` | левый край **карты** | позиции объектов, маски рельефа, миникарта, клик по ней |
| `planeX` / `planeZ` | левый край **полотна** (карта + поле) | UV текстуры, размер полотна |

Когда они совпадали, клетка `cx` отображалась содержимым клетки `cx − ring`, то есть вся
сцена уезжала на ширину поля по обеим осям. Ошибка держалась с самого начала, но была
незаметна: пока деревья стояли и на свободных, и на занятых клетках, рассогласование
не читалось. Заметной ошибка стала только после того, как наборы разложили по типам клеток.

Проверяется тестом `клетка → мир → клетка` (обязан вернуть ту же клетку) и сверкой
текстуры с типами из данных.

## Семантика типов клеток

Три типа клеток означают разное, и это проверяется, а не держится на памяти:

| Тип | Проходимость | Что на нём допустимо |
|-----|--------------|---------------------|
| Свободная | проходима | только проходимое: трава, куст, камыш, лилия, споры, галька |
| Дорога | проходима | плоский декор: галька, накат снега; выглядит по-разному в каждом наборе, но остаётся дорогой |
| Занятая | непроходима | препятствия: деревья, кактусы, валуны, базальт, грибы, ледяные шпили, кристаллы |

У каждого объекта в `BUILDERS` есть признак `solid`. `npm run check` падает, если `solid`-объект
попадёт в правила для свободных клеток или для дороги: такое дерево превратило бы свободную
клетку в непроходимую, а камень на дороге перекрыл бы проход.

На **занятой** клетке процедурных объектов больше нет: там пропсы из манифеста, и их
`solid` — это `land.solid` из манифеста, а не признак в `BUILDERS`. У плиток то же правило
проверяется отдельно: `tree`, `rock`, `debris`, `ruin` останавливают, `bush` и `bone`
проходимы, и `npm run check` падает на обоих направлениях.

Полный перечень объектов с разделением на проходимые и непроходимые — в
[`DECISIONS.md`](DECISIONS.md), раздел «Реестр объектов». Реестр слотов пропов (1…40) —
в [`docs/CONTEXT.md`](CONTEXT.md) в таблице выше и в файле кожи полем `tiles`.
