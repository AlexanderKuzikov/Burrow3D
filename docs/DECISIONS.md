# Burrow3D — DECISIONS

<!-- Append-only. Формат фиксирован. -->

## 2026-10-03: Три статических файла вместо сборки

**Контекст:** хочется, чтобы карту можно было открыть двойным кликом и переслать одним файлом,
и при этом добавлять наборы оформления и объекты без боли.

**Решение:** `index.html` (движок, inline-модуль) + `biomes.js` + `maps.js`. Three.js подключается
через `importmap` с CDN. Никаких `npm`, `vite`, `tsc`.

**Альтернативы:** (1) Vite + TypeScript — типизация и HMR, но появляется `node_modules`,
`dist/` и страница перестаёт открываться по `file://`; (2) один файл целиком — вырос бы за 2000
строк, править хирургически неудобно; (3) отдельные ES-модули в `<script type="module" src>` —
Chrome блокирует их по `file://` (origin `null`, CORS).

**Trade-off:** нет типизации и нет бандлинга; `node --check` проверяет только синтаксис,
всё остальное — глазами в браузере.

## 2026-10-03: Смысл символов карты задаётся интерфейсом, а не файлом

**Контекст:** формат карты не фиксирует, что означает символ. У пользователя `.` — трава,
`#` — дорога, `X` — лес, но другая карта может использовать `*` и `o`.

**Решение:** файл хранит только сетку. Три слота (свободная / дорога / занятая) назначаются
в панели; если в карте есть `.`, `#`, `X` — подставляются автоматически, иначе берутся самые
частые символы. Несопоставленные символы считаются свободными, и их список показывается в панели.
Кнопка «Сохранить» выгружает карту с приведённой легендой (`.` `#` `X`).

**Альтернативы:** (1) зашитый словарь `{'#': 'road'}` — ломается на любой другой карте;
(2) требовать в JSON поле `legend` — отвергнуто, файл должен оставаться минимальным.

**Trade-off:** при первом открытии чужой карты может понадобиться ручная правка слотов;
зато одна карта работает в любом наборе оформления без перегенерации.

## 2026-10-03: Обмен слотами легенды вместо запрета

**Контекст:** первая версия отклоняла выбор символа, если он уже занят другим слотом.
При трёх символах в карте это делало невозможным любую перестановку — интерфейс оказывался
в ловушке.

**Решение:** если выбранный глиф уже занят, слоты меняются местами.

**Альтернативы:** временно освобождать слот («пусто») — лишний состояние и лишний клик.

**Trade-off:** пользователь не может оставить два слота на одном символе, но и не попадает
в тупик.

## 2026-10-03: Данные карты не грузятся отдельным JSON

**Контекст:** при `file://` любой `fetch` соседнего файла блокируется CORS — страница показала бы
пустую сцену.

**Решение:** карта приходит через `FileReader` (кнопка или drag-and-drop), а не через `fetch`.
Встроенные демо объявлены литералом в `maps.js`.

**Альтернативы:** `fetch` с фолбэком на FileReader — лишняя ветка; base64 внутри HTML — нечитаемо.

**Trade-off:** автозагрузка карты по URL невозможна без сервера.

## 2026-10-03: Палитра земли — DataTexture, а не вершинные цвета

**Контекст:** нужно, чтобы границы клеток читались как границы клеток, а не размывались.

**Решение:** `DataTexture` размером «карта + кольцо», `magFilter = NearestFilter` (чётко вблизи),
`minFilter = LinearMipmapLinearFilter` (без мерцания вдали). Высота — вершинами плоскости.

**Альтернативы:** вершинные цвета — границы размываются интерполяцией; отдельная геометрия на
клетку — в 9216 раз больше draw call.

**Trade-off:** при сильном наклоне камеры на большой карте возможна пикселизация — это цена
за чёткий «картографический» вид.

## 2026-10-03: Высота рельефа — одна функция для меша и расстановки

**Контекст:** если меш и объекты считают высоту по-разному, деревья оказываются в воздухе
или в земле.

**Решение:** `terrainH(x, z)` — единственный источник. МешTerrain дискретизирует её, объекты
вызывают её же в точке размещения. Никаких raycast.

**Альтернативы:** raycast по готовому мешу — дороже и не нужен при аналитической функции.

**Trade-off:** функция должна оставаться чистой и дешёвой; при росте числа октав её стоит
кешировать.

## 2026-10-03: Туман задаётся долей от размера карты

**Контекст:** при загрузке карты 56×28 абсолютные границы тумана, настроенные под 96×96,
скрывали карту целиком в молоке.

**Решение:** в наборе оформления `fogK: [near, far]` — доли от `span` (наибольшей стороны).
Абсолютные `fogNear/fogFar` оставлены как запасной вариант.

**Альтернативы:** пересчитывать абсолютные значения в коде по типу карты — хрупко.

**Trade-off:** набор описывается в относительных единицах, абсолютное значение видно только
в отладчике.

## 2026-10-03: ridged-мультифрактал для гор

**Контекст:** «Горы» сначала выглядели как холмы. Причина: `fbm` усредняет октавы и сжимает
диапазон значений примерно до 0.45..0.55, поэтому `1 - |2n - 1|` даёт почти константу.

**Решение:** отдельная `fbmRidged` — гребни считаются пооктавно, каждый сглаживается предыдущим
слоем и возводится в степень 1.3. В наборе появился параметр `ridgedMid` для сдвига нуля.

**Альтернативы:** растянуть контраст `fbm` — ломает остальные наборы, где текущий вид нравится.

**Trade-off:** две функции шума вместо одной; `ridgedMid` приходится подбирать вручную.

## 2026-10-03: Части объекта — отдельные InstancedMesh, но одна геометрия через merge

**Контекст:** дерево состоит из ствола и двух конусов. Три `InstancedMesh` на дерево — это
десятки тысяч объектов в трёх draw call, но 19 объектов × 3 части дали бы ~50 вызовов на кадр.

**Решение:** у каждой части объекта своя `id`, на неё — свой `InstancedMesh` со своим материалом
(нужен для emissive и разной шероховатости). Мелкие детали внутри одной детали (листва, грибы
с пластинками, камешки) склеиваются через `mergeGeometries` в одну геометрию.

**Альтернативы:** один меш на объект с вершинными цветами и emissive в атрибутах — экономит
вызовы, но теряет per-instance emissive и усложняет материал.

**Trade-off:** 40–60 draw call на кадр — приемлемо для 60 fps.

## 2026-10-03: Грабли three.js r169, а не типичные ошибки

**Контекст:** три ошибки проявились одинаково — объекты теряли цвет, и диагностика по симптому
ушла бы не туда. Все три зафиксированы здесь, потому что они повторятся в любом проекте с
`InstancedMesh`.

**Решение:** зафиксировать в `AGENTS.md` и в knowledge base:

1. `setColorAt` требует `vertexColors: true` — иначе `color_fragment` не применяет `vColor`.
   В r169 **удалён** `Material.defaultAttributeValues`, поэтому отсутствующий атрибут `color`
   читается как (0,0,0): объекты становятся чёрными. Лечится белым атрибутом `color` на геометрии.
2. `setHSL` не конвертирует в рабочее пространство (в отличие от `setHex`), а `instanceColor`
   трактуется как linear — sRGB-lightness нужно задавать явно.
3. Байты в `DataTexture` пишутся в sRGB: считаем в linear, затем `convertLinearToSRGB()`, потом `* 255`.

**Альтернативы:** обойти `instanceColor` и красить через `onBeforeCompile` — больше кода и хрупче.

**Trade-off:** в проекте появился хелпер `whiteColors()` и обязательный параметр
`vertexColors: true`; это неочевидно и требует помнить при добавлении объектов.

## 2026-10-04: Кромка карты круглая, а кадр считается от размера карты

**Контекст:** у наборов без воды (пустыня, Марс, грибная чаща) был виден прямой угол
плоскости — местность читалась как плита, парящая в воздухе. Ребро плоскости считалось
как `max(|x|, |z|)`, то есть квадрат, и без воды за краем нечего было скрывать.

**Решение:** три связанных изменения.

1. Кромка считается по расстоянию: `e = hypot(x / halfW, z / halfD)` — остров круглый,
   углы плоскости уходят глубже и не читаются.
2. У наборов без воды поле вокруг карты вдвое шире (`ring` в `metricsFor`), обод отодвинут
   дальше — рельеф продолжается и тонет в тумане, а не обрывается.
3. Кадр, границы тумана и область теней считаются от размера **карты** (`M.frame`), а не от
   плоскости с полем (`M.span`). Иначе набор с широким полем отодвигал камеру в три раза
   дальше и карта превращалась в пятно вдали.

**Альтернативы:** (1) дать всем наборам воду — невозможно для пустыни и Марса по смыслу;
(2) прятать край туманом впритык — на высокой камере углы всё равно видны;
(3) увеличить плоскость втрое — та же проблема, что и с широким полем.

**Trade-off:** у наборов без воды текстура земли грузится вчетверо больше (поле 0.32 от
размера карты), сборка сцены на такой карте идёт дольше. Зато не нужно придумывать «водопровод»
ради маскировки геометрии.

**Что здесь устарело.** Пункты 1 и 2 отменены решением «Рельеф по типам клеток» (та же дата):
круглая кромка, отсчитанная от края полотна, съедала край карты (лес уходил под воду), а
широкое поле у наборов без воды прятало обрыв так далеко, что поверхность читалась плитой.
Читаемость края теперь даёт сам обрыв, отсчитываемый от границы карты. **Пункт 3 остаётся в
силе** и ни от чего не зависит.

## 2026-10-04: Проверка данных и тесты разделены

**Контекст:** ошибки вида «в наборе указан несуществующий объект» или «ключ `colors` не
совпадает с `id` части» проявляются только в браузере, и до тестов на них уходило время.

**Решение:** два уровня проверки.

- `scripts/check.js` — чистый Node, без зависимостей: парсит `maps.js` и `biomes.js` в `vm`,
  вытаскивает `BUILDERS` из `index.html` регуляркой и сверяет. Ловит битые карты, отсутствующие
  поля набора, неизвестные объекты, чужие `id` частей, неизвестные слои, неверные пары цветов.
- `tests/smoke.spec.js` — Playwright: страница в реальном Chromium, ошибки консоли, сборка сцены,
  переключение наборов и карт, легенда, слои, камера.

**Альтернативы:** только Playwright — медленно (1.6 мин) и не ловит ошибки данных без
открытия страницы; только `check.js` — не видит падения в рантайме.

**Trade-off:** два места, где нужно дописать проверку при добавлении новой сущности
(новый объект — в `BUILDERS`, новое правило — проверяется автоматически).

## 2026-10-04: Тип клетки определяет, что на ней может стоять

**Контекст:** три типа клеток — свободная, дорога, занятая — несут смысл проходимости.
Но в наборах деревья, кактусы, сосны, валуны и кристаллы стояли и на свободных клетках:
дерево на свободной клетке делает её непроходимой, то есть молча превращает свободную
в занятую. Камни на дороге перекрывают проход. Смысл карты при этом читался только визуально.

**Решение:** у каждого объекта в `BUILDERS` появился признак `solid` — непроходимый он или нет.
Распределение по наборам стало жёстким:

- `scatter.free` — только проходимое (трава, куст, камыш, лилия, споры, галька);
- `scatter.road` — только плоский проходимый декор; набор задаёт вид дороги через `ground.road`;
- `scatter.blocked` — препятствия.

**Альтернативы:** (1) оставить как было и полагаться на аккуратность — ровно то, что
и привело к ошибке; (2) проверять только в браузере глазами — не ловится, пока сцена
не отрендерится.

**Trade-off:** луга и долины стали пустоватыми — на них только низкая растительность.
Это честно по смыслу карты: если клетка свободна, её не занимает препятствие.

**Проверка:** `npm run check` сопоставляет `solid` с типом клетки и падает с указанием,
что перенести. Проверено намеренной ошибкой: дерево, возвращённое на свободную клетку,
даёт `FAIL набор «forest» → free → conifer: объект непроходимый, а стоял бы на свободной клетке`.

## 2026-10-04: Начало координат карты и полотна разведены

**Контекст:** рельеф рисуется на полотне шире карты — с полем вокруг, в которое уходит
берег. Текстура занимает всё полотно, а карта лежит внутри него со смещением `ring`.
Обе точки отсчёта хранились в одном поле `offX = -MX/2 - ring*CELL`, и оно же использовалось
для позиционирования клеток. В итоге клетка `cx` отображалась содержимым клетки `cx - ring`:
сцена была сдвинута на ширину поля по обеим осям.

**Решение:** два отдельных начала координат.

- `originX` / `originZ` — левый край карты. От него считаются позиции объектов, маски
  дорог и занятых участков, миникарта и клик по ней.
- `planeX` / `planeZ` — левый край полотна. От него считаются UV текстуры.

**Альтернативы:** (1) хранить одно начало и каждый раз прибавлять `ring` вручную в семи
местах — именно так и сломалось; (2) отказаться от поля и рисовать текстуру ровно по размеру
карты — тогда нет места для берега и кромки уезжает за край.

**Trade-off:** в структуре метрик на два поля больше, но `cellOf` / `cellToWorld` читаются
однозначно.

**Почему не поймали раньше.** Пока деревья стояли и на свободных, и на занятых клетках,
рассогласование в 13 клеток было не видно на глаз. Оно проявилось только после того, как
наборы разложили по типам клеток: лесные массивы оказались рядом с тёмными участками,
а сами участки остались пустыми.

**Проверка:** тест `клетка → мир → клетка` обязан вернуть ту же клетку, плюс сверка
текстуры с типами из данных (допуск 8% на шум палитры, при сдвиге расхождение 63%).
Проверено на сломанном коде: тест падает, на исправленном проходит.

## 2026-10-04: Реестр объектов

**Контекст:** признак `solid` разошёлся по девяти наборам оформления. Если его значение
не зафиксировано в одном месте, через полгода «кактус на свободной клетке» вернётся
незаметно: `npm run check` молчит, пока правило не нарушено, а глаз на общем плане
проходимое не отличит от непроходимого.

**Решение:** единственный источник правды — поле `solid` в `BUILDERS` в `index.html`,
оно же читается `scripts/check.js`. Реестр ниже — карта для человека, не для машины:
если он разойдётся с кодом, прав в код.

### Проходимые (`solid: false`) — можно ставить на свободную клетку и на дорогу

| Объект | Что это | Где используется |
|--------|--------|------------------|
| `tuft` | пучок травы, 3 наклонённых конуса | луг во всех наборах |
| `scrub` | сухой куст, 3 икосаэдра | пустыня, Марс, лесной подлесок |
| `reed` | камыш, 4 тонких конуса | болота Венеры |
| `lily` | кувшинка: круглый лист с цветком | болота Венеры |
| `spore` | светящаяся споровая точка, парит | Венера, грибная чаща |
| `mushroom` | маленький гриб: ножка и шляпка | Венера, грибная чаща |
| `pebble` | камушек | дорога во всех наборах |
| `drift` | снежный накат, приплюснутая сфера | горы, ледник, обочина |

### Непроходимые (`solid: true`) — только на занятую клетку

| Объект | Что это | Где используется |
|--------|--------|------------------|
| `conifer` | ель: ствол и два конуса | лес, горы |
| `pine` | сосна: ствол и три узких конуса | горы |
| `broadleaf` | лиственное: ствол и две кроны | лес |
| `cactus` | кактус: столб и два отростка | пустыня, Марс |
| `deadTree` | мёртвое дерево: ствол и три ветви | заготовлен, ни один набор не берёт |
| `boulder` | валун: три додекаэдра | пустыня, горы, Марс |
| `iceSpike` | ледяной шпиль | горы, ледник |
| `crystal` | кристалл-октаэдр с свечением | Марс, ледник, грибная чаща |
| `basalt` | базальтовая колонна, шестигранник | Марс |
| `giantMushroom` | гриб-исполин: толстая ножка, шляпка, светящиеся пластинки | Венера, грибная чаща |
| `vent` | вентиляционная трубка с лавой | заготовлен, ни один набор не берёт |

**Наблюдение:** `deadTree` и `vent` пока не используются ни одним набором. Это нормально —
`BUILDERS` это библиотека примитивов, а не набор текущего контента. Если они не нужны,
их стоит удалить, а не держать мёртвым кодом.

**Проверка:** `npm run check` падает на `solid`-объекте в `scatter.free` или `scatter.road`
и прямо называет, куда его перенести.

## 2026-10-04: Рельеф по типам клеток — обрыв от границы карты, дорога по среднему, горы на занятых

**Контекст:** три жалобы на вид, и все три — про одно свойство рельефа.

1. Край карты у части наборов уходил под воду или не читался совсем.
2. Набор «Горы» был бугристым по всей карте, а не горами.
3. Дорога шла неровно.

Прежний `terrainH` складывал высоту так:

```
h = (шум - mid) * amp
h *= 1 - roadFlatten*road - blockedFlat*blk     ← сглаживание умножением
e  = hypot(x / halfW, z / halfD)                  ← обрыв от края полотна
h -= smoothstep(rimStart, 1, e) * rimDrop
```

**Диагноз — замер на трёх демо-картах, все семь наборов.**

| Симптом | Причина | Замер |
|---------|---------|-------|
| край карты под водой | обрыв считался от края полотна, а не от границы карты, и потому съедал край | лес: медиана высоты по краю карты -19.7 при воде -11; ледник и горы тонули целиком |
| край то виден, то нет | `hypot` от нормализованных полуосей даёт эллипс, привязанный к соотношению сторон: короткая сторона почти не обрывалась. Наборам без воды поле делали втрое шире, и плоскость читалась плитой | пустыня на 56×28: медиана края -0.7 при разбросе 0.5 |
| дорога грубее местности | умножение на маску с резкой границей даёт уторок ровно на границе маски, тем больший, чем выше рельеф | 40×40, лес: ступенька между клетками дороги 1.9 против 0.4 на свободных |
| горы по всей карте | `ridged: true` применяло ridged-мультифрактал ко всей поверхности, а `blockedFlat` умел только *убрать* высоту, но не добавить | горы: свободные клетки от -57 до +21 |

**Решение:** четыре независимые части, и порядок между ними важнее каждой по отдельности.

1. **`rawH(x, z)`** — аналитическая функция: базовый fbm по всей карте, мелкая деталь и
   ridged-мультифрактал, **умноженный на размытую маску занятых клеток**. Маска размытая,
   поэтому у подножия массива выходит естественный переход, а не ступенька.
2. **Дорога** интерполируется к **сглаженной высоте**: `lerp(raw, hAvg, roadFlatten * road)`,
   где `hAvg` — сетка того же базового рельефа, размытая `boxBlur`. Обе функции непрерывны,
   поэтому уторок на границе дороги невозможен.
3. **Обрыв** отсчитывается от границы карты: `out` — расстояние наружу в клетках, делённое на
   ширину поля, и `rimDrop` не действует вообще внутри карты. Обе границы заданы в долях ширины
   поля (`rimStart`, `rimEnd`), поэтому у наборов с одинаковыми числами край выглядит одинаково
   на картах любого размера.
4. **Ширина поля одна для всех наборов** — 14% от большей стороны, минимум 6 клеток. Прежнее
   разветвление существовало потому, что читаемость края давало поле, а не обрыв; теперь её
   даёт обрыв, и поле держит только его склон.

**Про неотрицательность `fbmRidged`.** Из него нельзя вычитать среднее (`n - mid`): занятые
клетки местами провалились бы ниже базовой отметки и вместе с краем карты ушли бы под воду.
Поэтому массив только поднимается, а `ridgeMid` из схемы убран.

**Альтернативы:** (1) оставить умножение и уменьшить `roadFlatten` — уторок останется, просто
станет тише; (2) сглаживать дорогу только вдоль её оси — нужен обход графа дороги, это отдельный
алгоритм и отдельные грабли; (3) горы делать объектами, а не рельефом — теряется связь со
склоном: дорога перестаёт обходить массив, обрыв на краю перестаёт быть обрывом;
(4) дать всем наборам воду — по смыслу невозможно для пустыни и Марса.

**Trade-off:** сборка сцены выросла со 41–104 мс до 100–310 мс на карте 96×96 — добавились сетка
сглаженной высоты и ridged-мультифрактал в каждой вершине. Поле вокруг карты стало уже (у
наборов без воды было 32%), поэтому текстуры земли грузится меньше — это частично компенсирует.

**Проверка:** тест «край карты, дорога и горы ведут себя как задумано» гоняет все три демо-карты
на всех семи наборах и спрашивает ровно три вещи: край выше воды (кроме намеренно затопленных
наборов — им ставится `water.flood`), ступенька дороги не больше ступеньки свободных клеток,
свободные клетки дальше чем на 4 клетки от занятых остаются в базовом рельефе. На прежнем коде
тест падал по первым двум пунктам.

## 2026-10-04: Один автономный HTML; three.js вкладывается как data:-URL

**Контекст:** два запроса. Первый — «собрать всё в один HTML-файл». Второй — «чтобы карты
брались из той же папки, где лежит сам файл». Второй запрос выглядит противоречием первому,
но это не так: код и демо-карты живут внутри файла, пользовательские карты — рядом.

**Проверка, на которой стоит решение.** Прежде чем писать сборщик, проверено на `file://`:
модуль three.js грузится из `data:`-URL через importmap. Отдельно проверено, что `blob:`-URL
с `import()` тоже возможен, но в нём нужна ручная перезапись `</script` при встраивании —
без неё исходник ломается. Проверка сделана до реализации, потому что от ответа зависел выбор.

**Решение: three.js как `data:`-URL в importmap.**

```json
{"imports":{
  "three":"data:text/javascript;base64,…",
  "three/addons/controls/OrbitControls.js":"data:text/javascript;base64,…",
  "three/addons/utils/BufferGeometryUtils.js":"data:text/javascript;base64,…"
}}
```

1. **Исходники three.js не трогаем вообще.** Они чужие и меняются с каждой версией; любая
   правка их исходников — это долг, который всплывёт при обновлении версии.
2. **Аддоны адресуются точными путями**, а не префиксом `"three/addons/"`. Префиксное
   сопоставление дописывает остаток пути относительно значения, а относительно `data:`-URL
   это невозможно. Движок импортирует ровно два аддона по полным путям, поэтому хватает точных.
3. **Каждая подстановка обязана состояться ровно один раз.** `replaceOnce` падает, если
   совпадений ноль или два. Молчаливый промах дал бы нерабочий артефакт с сообщением об
   успешной сборке — худший вид поломки.
4. **Артефакт проверяется тестом на `file://` с перехватом запросов.** Смысл офлайн-файла —
   в отсутствии сети, поэтому тест ловит *любой* запрос наружу, а не только падение сцены.
5. **Сторож загрузки three.js с CDN вырезается.** В офлайн-файле сети нет по определению, и
   сообщение «не загрузилось с CDN» было бы ложным. `__MAP_READY = false` остаётся: на нём
   висят автотесты.

**Альтернативы:** (1) склеить модули вручную — срезать `export { … }`, заменить
`import { X } from 'three'` на деструктуризацию из локального объекта. Файл на 500 КБ меньше,
но это правка чужих исходников: любая новая версия three может принести форму экспорта,
которую скрипт не распознает, и сборка станет тихо неверной. Отклонено. (2) Подключить esbuild —
надёжнее склейки, но добавляет зависимость и узел в проект, которому она не нужна для
разработки. (3) Класть three.js отдельным файлом рядом — это уже не «один файл».
(4) Не вкладывать three.js вовсе, оставить CDN — файл в 33 КБ, но офлайн не закрыт, а
именно его и просили.

**Про «карты из своей папки».** Автопоиск невозможен: браузер не умеет перечислять файлы
в каталоге, а `fetch` на `file://` заблокирован. Отсюда `<input type="file" webkitdirectory>` —
выбор папки пользователем, и это единственный путь, работающий и по `file://`, и по HTTP.
Проверено: по HTTP работал бы и автопоиск, но только через манифест (`maps.json` рядом) либо
парсинг листинга каталога — два лишних формата и лишняя точка отказа ради сценария, который
закрывается выбором папки. Отклонено как YAGNI; если понадобится, это отдельное решение.

**Trade-off:** `dist/burrow3d.html` весит 1.83 МБ (base64 добавляет треть к 1.37 МБ исходников).
Это цена автономности. В репозиторий артефакт не попадает — он воспроизводится
`npm run build`, а исходным файлом приложения по-прежнему остаётся `index.html`.

**Проверка:** `npm test`, сценарий «собранный файл самодостаточен» — грузит `dist/burrow3d.html`
по `file://`, ждёт сцены, переключает все наборы и требует нулевого числа запросов наружу.
Пропускает себя, если `dist/` нет, чтобы `npm test` работал и без сборки.

## 2026-10-04: Выгрузка кожи — плотности по блокам вместо параметров шума

**Контекст:** решение владельца от 2026-10-04: Burrow3D — инструмент, который рождает вид и
отдаёт его данными; ландшафт здесь, башни и существа — в `NexusDefense`. Значит, игре нужен
контракт, который переживёт новые наборы и новые объекты без правки.

**Главное решение: в контракт уходят плотности, а не параметры шума.**

1. Если отдать игре `freq/bias/gain`, ей придётся реализовать `fbm` заново. Это вторая
   реализация того же шума, а вторая реализация расходится с первой на первой же правке
   набора — и расхождение будет выглядеть как «движок сломался», а не как «у нас тут две
   формулы».
2. Вместо этого в файле лежит `density`: сколько объектов правила ожидается в блоке
   `8 × 8` клеток, посчитанное по клеткам нужного типа. Это обязательство исполняется всегда,
   и игра не должна знать ничего, кроме разброса внутри блока.
3. Значит, формулу расстановки нельзя дублировать. Добавлена `ruleDensity()` — математическое
   ожидание цикла `buildScatter`. Обе ветви цикла (`per >= 1` и `per < 1`) дают в среднем
   ровно `per`, поэтому формула одна.
4. **Связь хрупкая, и это записано граблями:** если поменять только цикл, скин начнёт врать,
   и заметят это только глаза. Ловит тест, сравнивающий сумму плотностей с реальным числом
   объектов. Расхождение по всем наборам — меньше 1 %.

**Второе решение: в контракте нет перечислений.** Ни списка наборов, ни списка объектов, ни
«известных» имён. `builder` в правиле — имя для чтения человеком; игра по нему ничего не
ищет, иначе первый же новый объект потребовал бы правки в игре. Всё для рисования лежит в
самом правиле: эффективные цвета каждой части, разрешённый `layer`, `scale` всегда парой,
`jitter`, `tilt`, `solid`.

**Третье решение: `npm run check` проверяет выгруженное и падает на устаревшей коже.**

- Чек читает `dist/skins/*.json` и сверяет: `builder` есть в `BUILDERS`, `solid` совпадает с
  ним, `solid: true` не встречается у свободной клетки и дороги, плотности в `0..`, длина
  сетки равна `ceil(w/cell) × ceil(h/cell)`, `map.hash` совпадает с картой, состав правил
  совпадает с `biomes.js`.
- Требуется скин **каждого** набора: иначе чек прошёл бы на пустом месте, проверив один файл
  вместо семи.
- Проверка состава правил — это проверка свежести. Владелец добавил объект, забыл
  перевыгрузить — чек валит с прямым текстом. Это ровно то поведение, ради которого чек
  читает выгрузку, а не исходники.
- Чек остаётся чистым Node без зависимостей и сам экспорт не запускает: `npm run export`
  требует браузера, потому что экспортёр живёт в движке. Отсюда порядок
  `npm run export && npm run check && npm test`.

**Четвёртое решение: пакетный экспорт идёт через браузер.** `scripts/export.js` открывает
страницу и зовёт ровно ту функцию `skinJson()`, что и кнопка. Своя реализация выгрузки в
Node разошлась бы с браузерной, а проверить это было бы нечем.

**Альтернативы:** (1) отдать параметры шума — вторая реализация в игре, отклонено выше.
(2) Отдать список инстансов с координатами — файл раздувается на порядки и привязывает игру к
нашей сетке клеток; плотности как раз этого и не требуют. (3) Держать отдельную таблицу
плотностей в `biomes.js` рядом с правилами — разъедется сама с собой при первой правке
правила. (4) Считать плотности в `check.js` — чек остался бы чистым, но перестал бы
проверять то, что уедет в игру, и не увидел бы устаревшую кожу.

**Что осталось за рамками и требует `version: 2`:** высоты парения части (`float` у спор) в
формате нет, поэтому игра не повторит парящие споры. Поле добавится вместе с выгрузкой
геометрии — сейчас оно (`geometry: null`) уже в контракте, чтобы форма не поехала позже.
Записано в открытые проблемы.

**Проверка:** тест «кожа выгружается детерминированно, читается обратно и совпадает с
картинкой» на карте 96×96 — худший случай по размеру сетки плотностей: две выгрузки подряд
побайтово равны, файл читается назад и проходит проверки формы, кнопка «Выгрузить кожу»
отдаёт файл с именем из имени набора и тем же содержимым. Плюс 15 негативных контролей на
`npm run check` — каждый ломает скин осмысленно и каждый пойман.
